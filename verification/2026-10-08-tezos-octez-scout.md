## Distinct question and cheap falsifier

The exact tagged [`gs_transport_connection.ml`](https://gitlab.com/tezos/tezos/-/blob/octez-v25.2/src/lib_dal_node/gossipsub/gs_transport_connection.ml) receives a `Message_with_header`, starts `app_in_callback` with `Lwt.dont_wait`, then enqueues `In_message` through `bounded_p2p_input`. Tagged [`daemon.ml`](https://gitlab.com/tezos/tezos/-/blob/octez-v25.2/src/lib_dal_node/daemon.ml) can await `Node_context.fetch_committees` in that callback for an attester-profile node; tagged [`node_context.ml`](https://gitlab.com/tezos/tezos/-/blob/octez-v25.2/src/lib_dal_node/node_context.ml) deduplicates a common in-flight committee fetch but does not visibly cap the number of waiting caller promises. First-party [MR !22542](https://gitlab.com/tezos/tezos/-/merge_requests/22542) documents the asynchronous callback change and notes crafted raw P2P messages are non-trivial to synthesize. First-party [MR !22611](https://gitlab.com/tezos/tezos/-/merge_requests/22611) adds an 8,192-entry Gossipsub worker input cap after that callback spawn; it describes prior independent OOM paths but does not itself prove this proposed composition.

**Decisive local question:** can more than 8,192 locally generated, well-formed DAL messages leave more than 8,192 outstanding application callback promises when committee lookup is deliberately slow, despite the worker input cap? First run a one-function mock-callback harness against the pinned source, with the same message sequence and a fast callback as control. Stop if callbacks are bounded elsewhere or no longer exist beyond the queue cap; retain only the observed callback-count and memory delta if the control differs. Then separately establish peer reachability, realistic cost, actual material node availability impact, supported configuration/deployment and full known-issue overlap before any severity or bounty claim.

## Tagged-source peer gate check (read-only, 2026-10-08)

An independent review of pinned commit `f606285304de0294926946b8b474a1e38a5b5972` found no upstream 8,192-message gate. A peer must first pass [P2P authentication](https://gitlab.com/tezos/tezos/-/blob/f606285304de0294926946b8b474a1e38a5b5972/src/lib_p2p/p2p_socket.ml#L401-431), network compatibility, and a free connection slot; the [DAL defaults are public mode](https://gitlab.com/tezos/tezos/-/blob/f606285304de0294926946b8b474a1e38a5b5972/src/lib_dal_node/gossipsub/transport_layer_default_parameters.ml#L99-120). After connection, application messages have [no per-message throttle](https://gitlab.com/tezos/tezos/-/blob/f606285304de0294926946b8b474a1e38a5b5972/src/lib_p2p/p2p_protocol.ml#L123-142); the [DAL defaults](https://gitlab.com/tezos/tezos/-/blob/f606285304de0294926946b8b474a1e38a5b5972/src/lib_dal_node/gossipsub/transport_layer_default_parameters.ml#L53-67) do not set download-speed or incoming-message-count limits. The 16 KiB read buffer is reusable I/O storage, not a count cap. Bad wire encoding is rejected and greylisted; cryptographic shard and Gossipsub validation occurs [later in the worker](https://gitlab.com/tezos/tezos/-/blob/f606285304de0294926946b8b474a1e38a5b5972/src/lib_gossipsub/gossipsub_worker.ml#L851-860).

The [handler](https://gitlab.com/tezos/tezos/-/blob/f606285304de0294926946b8b474a1e38a5b5972/src/lib_dal_node/gossipsub/gs_transport_connection.ml#L121-142) starts the callback before the [8,192-entry worker queue](https://gitlab.com/tezos/tezos/-/blob/f606285304de0294926946b8b474a1e38a5b5972/src/lib_gossipsub/gossipsub_worker.ml#L1039-1055) checks fullness. The message ID has a 16-bit shard index, allowing syntactically distinct decodable IDs; this **does not** establish valid shards. Committee fetches for the same level share an in-flight promise, so there is no supported claim of multiplied L1 RPCs. The source supports a possible accumulation of waiting callbacks from an ordinary connected peer, **not** measured throughput, memory exhaustion, or availability impact. Those remain UNKNOWN pending a local same-state test.
