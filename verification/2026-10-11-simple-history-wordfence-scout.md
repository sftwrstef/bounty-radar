## Declared trust-boundary question and cheapest falsifier

Can an unauthenticated commenter place markup in a comment author/content field that survives into the Simple History admin event HTML as stored XSS? This is a genuine public-input-to-privileged-view boundary, and would fit Wordfence's stored-XSS class only if script execution were reproducible in a default setup.

Cheapest executable falsifier if revisited: in an isolated WordPress + Simple History 5.35.0 site, submit one synthetic anonymous comment with harmless inert markup markers in author and body, open the generated event as admin, and compare DOM text/markup plus a normal-comment control. Do not test another person's site. This executable test was **not run** in this pass.

The pinned-source trace currently weighs against the hypothesis: [`class-comments-logger.php`](https://github.com/bonny/WordPress-Simple-History/blob/a404946c1c400e14d30234a6895c4ccd627ee724/loggers/class-comments-logger.php#L612-L643) escapes author fields in the message and applies `esc_html` to comment body before `wpautop`; the detail view sends only that escaped body to its RAW formatter, while [`Event_Details_Item_Formatter`](https://github.com/bonny/WordPress-Simple-History/blob/a404946c1c400e14d30234a6895c4ccd627ee724/inc/event-details/class-event-details-item-formatter.php#L52-L74) escapes ordinary detail values. The current release changelog also names event-text escaping hardening. No source-supported XSS claim remains from these fields. This does not prove all loggers or UI renderers safe, and does not exhaust the target.

## Bounded second field: Subscriber display name — source kill, no runtime test

Decisive question: if a Subscriber edits their own display name, does Simple History 5.35.0 store it in a profile-change event and interpolate it into admin-facing event HTML without context-appropriate escaping? Stopping condition: an exact-tag source trace showing the field is not logged/reachable, is escaped before HTML, or is exposed unescaped. Only the last result justifies an isolated local diagnostic; source kill means no executable test. This is distinct from the anonymous comment author/body path above. Budget: one bounded source screen; no live WordPress site or target interaction.

Result at exact tag `a404946c1c400e14d30234a6895c4ccd627ee724`: **SOURCE-KILL for the display-name event-rendering hypothesis**. The profile-change path is plausible for an ordinary user editing their own profile but was not exercised in WordPress. The logger includes `display_name` in [`PROFILE_FIELDS_TO_DIFF`](https://github.com/bonny/WordPress-Simple-History/blob/a404946c1c400e14d30234a6895c4ccd627ee724/loggers/class-user-logger.php#L741-L765), collects the submitted field in [`on_pre_insert_user_data_collect`](https://github.com/bonny/WordPress-Simple-History/blob/a404946c1c400e14d30234a6895c4ccd627ee724/loggers/class-user-logger.php#L789-L884), and commits a `user_updated_profile` event when changed ([lines 675–714](https://github.com/bonny/WordPress-Simple-History/blob/a404946c1c400e14d30234a6895c4ccd627ee724/loggers/class-user-logger.php#L675-L714)). The changed value is shown as an old/new `display_name` detail ([lines 1587–1592, 1623–1655](https://github.com/bonny/WordPress-Simple-History/blob/a404946c1c400e14d30234a6895c4ccd627ee724/loggers/class-user-logger.php#L1587-L1655)); no custom/raw formatter is set for this item. The group uses the table formatter, whose item formatter calls [`get_value_diff_output()`](https://github.com/bonny/WordPress-Simple-History/blob/a404946c1c400e14d30234a6895c4ccd627ee724/inc/event-details/class-event-details-item-table-row-formatter.php#L14-L22); that method applies `esc_html` to both new and old values ([lines 52–74](https://github.com/bonny/WordPress-Simple-History/blob/a404946c1c400e14d30234a6895c4ccd627ee724/inc/event-details/class-event-details-item-formatter.php#L52-L74)). The REST field `details_html` is inserted by React with `dangerouslySetInnerHTML`, but the untrusted display-name diff has already been escaped before that sink ([REST lines 1329–1335](https://github.com/bonny/WordPress-Simple-History/blob/a404946c1c400e14d30234a6895c4ccd627ee724/inc/class-wp-rest-events-controller.php#L1329-L1335), [component lines 9–21](https://github.com/bonny/WordPress-Simple-History/blob/a404946c1c400e14d30234a6895c4ccd627ee724/src/components/EventDetails.jsx#L9-L21)). The main `user_updated_profile` event text links the profile but does not interpolate the new display name ([logger lines 1052–1081](https://github.com/bonny/WordPress-Simple-History/blob/a404946c1c400e14d30234a6895c4ccd627ee724/loggers/class-user-logger.php#L1052-L1081)).

There is a second display path: REST reads the *current* user object's `display_name` into `initiator_data` ([lines 1357–1378](https://github.com/bonny/WordPress-Simple-History/blob/a404946c1c400e14d30234a6895c4ccd627ee724/inc/class-wp-rest-events-controller.php#L1357-L1378)). This is a React text-rendering boundary, not an HTML injection route in the traced code.
